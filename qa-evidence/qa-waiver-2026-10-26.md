## What the author did check

1. **Syntax.** `bash -n scripts/install-minimax-m31-flash-vq.sh` exits 0. No shell
   static analyser is installed on this machine (`shellcheck`, `shfmt`, `bashate`,
   `checkbashisms` all absent — the same finding the 2026-10-18 record made), so syntax
   plus execution is the static evidence available.

2. **The script's own contract, executed.** `bash scripts/install-minimax-m31-flash-vq.sh
   selftest` exits 0 and prints:

```
minimax31: parts:    61 names, sizes summing to 115526325376 bytes (107.59 GiB) = PAYLOAD_BYTES
minimax31: layers:   57 MoE layers: 7 small R13, 30 large R13, 20 R13+8
minimax31: splits:   resident 111333740672 ok, read while serving 4192584704 ok
minimax31: sidecars: 7 fetched, 6 of them listed in SHA256SUMS (it cannot list itself)
minimax31: mtp:      on with 3 proposals
minimax31: selftest: the script's own contract holds
```

   The same action was falsified on purpose: `MINIMAX31_DRAFT=1 ... selftest` warns that
   the family accepts 2 to 7 proposals and exits 1, so the action is not a rubber stamp.

3. **The script's taxonomy against the artifact's own contract.** Every one of the 61
   part sizes the script expects was compared with `release.json`'s `parts` array
   (fetched from the Hub during this unit) and with `r13p8_layers`: 61 parts, 0 size
   mismatches, the twenty residual layers identical to the release's list, and the part
   sizes summing to the published 115,526,325,376.

4. **The fetch list against the revision's listing.** All 20 named non-part files exist
   in the pinned revision, all 61 GGUFs are at the repository root (so the
   `--include "*.gguf"` pattern takes exactly them), and the fetch therefore takes 81 of
   the revision's 227 files.

5. **The pinned revision's weights are the measured revision's weights.** `release.json`
   and `SHA256SUMS` hash the same at `2789cbaf` (the pin) and at
   `74e5a9fd12fb57a5c1babb559536cf10733939ea` (the revision the engine's docs and the
   card's measurements name): 61 parts, 0 digest differences, and every part digest in
   `release.json` matches its `SHA256SUMS` line at both. This is what lets the contract
   cite the author's measurements without claiming they were taken on these bytes.

6. **The installer's guards, exercised on a sparse fixture** built from the real
   `release.json` and `SHA256SUMS` plus `truncate`d parts at the published sizes
   (`/tmp/mmfixture/release`, 68 files, 107.59 GiB apparent):
   - `plan` and `status` print the release state, both directories, the launch line and
     the disk need without touching the network;
   - `verify` against a `SHA256SUMS` generated from the fixture's own contents reports
     67 matching digest lines, writes the size/mtime record, and then reports the
     record as matching;
   - `verify` with one digest corrupted reports `body-nonexpert.gguf: FAILED` and exits
     1 without writing a record;
   - `touch`ing one part makes `status` report `verification record STALE - run verify`
     and makes `start` refuse with the command that fixes it;
   - `start` with no record at all refuses before doing anything else;
   - `preflight` names a stray `.gguf` the release does not declare, a part present at
     the wrong size, a partial file in flight, insufficient room for the fetch, and
     insufficient room for the K/V tier — and exits 1.

7. **The derived numbers were recomputed, not copied.** The resident split (111,333,740,672
   bytes), the read-while-serving split (4,192,584,704), the tier sizes at 1M and 512K
   and the memory rows all come from the artifact's own `memory-budget.json` and
   `release.json`, which are the two files the recipe cites for them.

8. **Links and cross-references.** Every relative link in the new recipe, the new
   runbook and the README resolves to a file in the repository (checked by script; zero

# The MiniMax unit, extended the same evening: the serial lane and the 1M context

**What changed:** the unit's branch gained `f2ce777` (verify's two tiers, and a 524288
served context) and `e977474` (the serial-lane flags, and the served context back to the
model's native 1,048,576 by operator decision). Both are covered by the same waiver; this
section exists so the extra evidence is on the record too.

**What the author did check**

1. The first Spark start was rejected before it loaded anything:

```
error: minimax_m3_vq MTP runs only on the serial lane (mtp_lane)
ds4-server-rs: serving plan rejected unsupported options
```

   The cause is in the engine's own source, read from main: `resolve_mtp` turns MTP off
   with that error for a serial-lane family whenever `bank_driver()` reports the driver
   present, and `bank_driver()` is present for any `--max-seqs` width on a persistent-bank
   family unless the serial route is selected. The launcher was passing a width and the
   drafter together.
2. The route selection is the author's own, not an invention: `docs/serving-contract.md`
   in the local checkout at /data/ds4-dfm-rs says `--cont-width 0` and
   `DS4_SERVER_COALESCE_MAX=0` keep the legacy serial meaning with no bank lane, and that
   `DS4_SERVER_CONTINUOUS=0` forces the static/serial route; the resolved plan emits
   `DS4_SERVER_CONTINUOUS=0` itself for this case (`ResolvedPlan::env_overrides`). The
   launcher now passes both with the drafter armed.
3. `--max-seqs` accepts only `auto` or 1..64 (`MaxSeqs::parse`), so `0` is never passed as
   a width; `--cont-width` is the hidden alias that accepts it.
4. The engine requirement itself was corrected from source: PR #110 ("Add the
   MiniMax-M3.1-Flash VQ family") is merged, 2026-10-25T02:33:10Z at head `4988ae7`, and
   main carries `crates/ds4-core/src/minimax_vq.rs`. The earlier claim that the family
   exists only on an unmerged branch was wrong and is corrected in every file that made it.
5. `plan` prints both shapes; `selftest` passes with the native context and still checks
   the tier arithmetic.

**What remains unverified**

- The lane flags have not been exercised against a live boot. The next start on the Spark
  is the first test of them, and no decode rate, engine quote or TTFT exists for this
  artifact anywhere.
- The 1M shape is the card's plan, and its author measured 114.75 GiB peak on it with the
  drafter, which he calls unsafe beside anything else on a 128 GB host.
