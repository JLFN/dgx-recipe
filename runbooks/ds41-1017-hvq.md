# Recipe: DeepSeek-V4.1-Flash-1017 hVQ on the DS4 CUDA engine

DeepSeek's October 17 V4.1 Flash checkpoint through YoungAi's
`vq8sh14-q4k-mtpnative` quantization, then refit twice: iVQ weighted each routed
expert's code assignment by that expert's own input second moment, and hVQ added
the off-diagonal of that matrix, feeding each 8-weight block's error forward into
the blocks after it. The result is one 113.56 GB base GGUF that carries the
model's three DSpark draft towers, a 971 MB vision sidecar, and the 1017 Engram
tables read from disk, at the native 1,048,576 context.

- Contract: [`recipes/ds41-1017-hvq.yaml`](../recipes/ds41-1017-hvq.yaml)
- Installer: [`scripts/install-ds41-1017-hvq.sh`](../scripts/install-ds41-1017-hvq.sh)
- Artifact: [`Baekpica/DeepSeek-V4.1-Flash-1017-hVQ-GGUF`](https://huggingface.co/Baekpica/DeepSeek-V4.1-Flash-1017-hVQ-GGUF) at `0d3cae07`
- Source checkpoint: `deepseek-ai/DeepSeek-V4.1-Flash-1017` at `1bae0e10`

## What this is, and what it is not

It is the operational half of the artifact: the exact file set, the assembly, the
launch shape, the four digests that separate this release from the four other 1017
packagings that share its file names and sizes, and the guard that keeps a wrong
file out of the serving path. It is also the first DeepSeek recipe here whose
artifact was measured on a DGX Spark by its author, so for once the speed and
fidelity figures describe these bytes and not a predecessor's.

It is not a measurement by this repository. Nothing of this artifact has been
fetched, assembled, loaded or requested on the reference Spark. The author's
numbers are printed below with the engine commit he used, and the box's own state
is printed as it was read on 2026-11-13.

The mechanism is worth one paragraph, because it explains why the file can be
better than VQ while its weights are further away. A routed expert is cut into
8-weight vectors along each row. VQ picks the nearest codeword for each vector
against the weights alone. iVQ picks it against the weights scaled by how strongly
real inputs drive each channel. hVQ assigns the blocks of a row in order under
`H_t = D^(1/2) ((1 - t) I + t R) D^(1/2)` with `t = 1`, where `R` is the
correlation of the expert's inputs, and after each block it adds what that block's
error leaves on the later blocks to their targets. The error that remains on
correlated channels therefore cancels in the expert's output instead of adding up.
Everything outside the 40 expert blobs is the VQ base's bytes, byte for byte.

## Where the pieces go, and why

`--gguf-dir` (default `/mnt/models/ds41-1017-hvq`) holds the 40 parts and the base
they assemble into. The base is read once at load and then stays resident at about
106 GiB, so disk speed stops mattering after the first minutes and the roomy
volume is its right home.

`--dir` (default `$HOME/models/ds41-1017-hvq`) holds the vision sidecar, the logs
and the pid files. The vision tower is read from disk when an image arrives, on
the first image after a cold start or an eviction.

`--engram-dir` (default: a verified existing copy of the published sizes under
`$HOME/models`, else `<--dir>/deepseek-engram`) holds the two n-gram tables, read
in rows on the tokens that hit an n-gram, which is why they belong on the NVMe.
Each candidate is checked as it stands and one level deeper, because a copy
fetched by this repository's own path arrives inside a `deepseek-engram/`
subdirectory.

That is where the box actually keeps things, read on 2026-11-13 through the gvfs
mount rather than remembered: `/mnt/models` holds the base GGUFs (`gemma-4-26B-A4B-it`,
`gemma-4-26b-a4b-vq-gguf`, `mimo26-unc`, `Qwen3.8-…-SSD-PLE-GGUF`, `spark-x2.6-4b-vq-2s`)
and `$HOME/models` holds what a running server reads, plus the logs
(`Bonsai-2_27B`, `Ternary-Bonsai-2-27B-PQ2_0.gguf`, `ds41-1017-unc`, `logs/`,
`mimo26-unc`, the Qwen PLE directory). The two volumes have 675 GB and 677 GB free
respectively, so both halves of this artifact fit with room to spare.

## Quick start on the Spark

```bash
bash scripts/install-ds41-1017-hvq.sh selftest    # no payload; checks the constants against the manifest
bash scripts/install-ds41-1017-hvq.sh preflight
bash scripts/install-ds41-1017-hvq.sh download    # 316.6 GB here, resumable
bash scripts/install-ds41-1017-hvq.sh assemble    # 40 parts -> the base, each hash-checked
bash scripts/install-ds41-1017-hvq.sh verify      # reads everything; writes the verification record
bash scripts/install-ds41-1017-hvq.sh build       # make cuda-spark, then the engine floor
bash scripts/install-ds41-1017-hvq.sh start       # 0.0.0.0:8014, under a memory watchdog
```

`install` runs all of that in order and then starts. `plan`, `stop`, `status`,
`logs` and `test` round it out, and every path, port and memory knob is a flag or
an environment variable documented in the script header. `--no-vision` serves text
only; `--mtp-mode off|auto|on` controls the embedded drafter and defaults to the
card's `auto`.

`selftest` is new in this launcher and needs nothing downloaded: it builds the 40
part names, checks that the part sizes add up to the base and that the payload
arithmetic holds, compares the four hardcoded digests and all 40 part names with
the manifest at the pinned revision, and exercises the verification record's
staleness logic by writing one, accepting it, then creating a file it fingerprints
and requiring the record to go stale. It passed against the live manifest on
2026-11-13.

## The trap: five bases, one name, one size

Five packagings now ship a file named exactly
`DeepSeek-V4.1-Flash-vq8sh14-q4k-mtpnative.gguf` at exactly 113,556,639,424 bytes:

| Release | Base SHA-256 | What it is |
|---|---|---|
| `DeepSeek-V4.1-Flash-1017-hVQ-GGUF` | `d000e791…` | this one: error feedback through the input correlation |
| `DeepSeek-V4.1-Flash-1017-iVQ-GGUF` | `746fb52d…` | diagonal-only input weighting |
| `DeepSeek-V4.1-Flash-1017-VQ-GGUF` | `9f3afe6a…` | YoungAi's codebooks from the weights alone |
| `DeepSeek-V4.1-Flash-1017-UNCENSORED-VQ-GGUF` | `2680747e…` | VQ on dealignai's refusal-removed checkpoint |
| `wenzhouwu/YoungAi-DeepSeek-V4.1-Flash-1017` | `0da4ae2d…` | YoungAi's own packaging of the same checkpoint |

The parts look alike and are not interchangeable: a directory holding one
release's parts beside another's `SHA256SUMS` fails at the first part, and a
directory holding one release's parts beside another's manifest assembles into a
base that fails the final digest after 113 GB of download. The installer prevents
both by checking every part against the manifest as it appends it and the
assembled file against `d000e791` at the end.

Two more silent mismatches are possible for the smaller files, and neither is
visible by looking:

| File | This release | What else answers to that name |
|---|---|---|
| `deepseek-engram/model-0004{7,8}-of-00048.safetensors` | 1017 tables: `76a05106…`, `9dc51433…` | the older V4.1 tables, same names, same sizes, `824db488…` and `976330f4…` |
| `DeepSeek-V4.1-Flash.vision.gguf` | `3a8b194a…`, also the VQ and iVQ sidecar | the older V4.1 sidecar, same size, 532,623,100 bytes different |

The engine takes the Engram file names from the GGUF header and loads whatever sits
at those names, so a directory holding the V4.1 tables runs a mismatched model
without a word. The installer names the wrong digests when it sees them rather than
reporting "unknown", and `verify` says which set it found.

## The second trap: the Engram tables arrive one directory too deep

The two tables are the only payload of this release that the repository keeps in a
subdirectory, and the Hugging Face CLI preserves the repository path under
`--local-dir`. A fetch of `--include "deepseek-engram/*"` into a directory writes
`<dir>/deepseek-engram/model-0004{7,8}-of-00048.safetensors`, not
`<dir>/model-0004{7,8}-of-00048.safetensors`, while the parts, the manifest, the
docs and the sidecar (all at the root) land exactly where the script looks for
them.

Measured on 2026-10-18 against `huggingface_hub` 1.23.0 with the sibling
repository: a fetch of a 264 KB subdirectory file with
`--include "docs/*" --local-dir X` produced `X/docs/img/…`, and a top-level include
produced `X/<file>`. `download` and `verify` now adopt that layout: if the tables
are complete one level deep and the top level is empty, the script moves them up
with `mv`, which is a rename on one filesystem and copies no bytes. If a mount
point sits between the two directories it refuses instead of silently copying
203 GB, `status` names the nested layout, and `start` points at `verify` rather
than calling the tables missing.

## Why start demands a verification record

Hashing the four identity files costs a full read of the payload — 317 GB — and an
earlier shape of this launcher paid it on every `status`, which made the script
look hung. The work is done once, by `verify`, which writes `.verified` in the
state directory with the digests it proved plus the size and mtime of the base, the
sidecar and both tables. `start` refuses to serve unless that record still matches
the bytes on disk, so a table set swapped afterwards for one of the same size is
caught by the mtime.

`verify` is deliberately explicit and counted: it checks the 40 parts (or the
assembled base) one by one against `SHA256SUMS`, then the vision digest, then both
table digests. It does not rely on `sha256sum -c --ignore-missing` alone, because on
a directory where none of the listed files exist that command exits 0 without
verifying anything — measured on 2026-10-18 while building the sibling recipe.

## Resuming across a restart: the K/V disk store

A restart normally pays the prefill again, and on this artifact that is the expensive
half: the author's sweep is 1,291 to 1,717 tok/s of prompt processing, so a 64K prompt
is a minute of work that a restart throws away. `--kv-disk-dir` is what keeps it. The
engine writes two checkpoints into that directory, `K_pre` after the prefill and before
the first token, and `K_turn` when the run ends; a restore tries `K_turn` first and
falls through to `K_pre`. The checkpoint's trailer carries the mount digest, so state
written by another artifact is never imported.

It is off unless you ask for it:

    bash ~/dgx-recipe/scripts/install-ds41-1017-hvq.sh \
        --kv-disk-dir "$HOME/models/ds41-1017-hvq/kv" --kv-disk-space-mb 8192 start

or the same values in `KV_DISK_DIR` and `KV_DISK_SPACE_MB`. The budget defaults to the
engine's own 4096 MB (`DS4_KVSTORE_DEFAULT_MB`) and bounds the store, so a prompt whose
checkpoint does not fit is simply not kept; the engine's measured turn checkpoint was
20.7 MB for 3,773 tokens. `preflight` requires the binary to advertise `--kv-disk-dir`
only when `start` will pass it, and checks that the directory can be created and holds
more than the budget. `plan` and `status` print the directory, the budget and the free
space, and `status` says plainly when the store is off.

What it does not do: it is not a model cache. The 113.6 GB base is still mapped on every
start, and the card's 153 s to resident is unchanged. It saves the prefill, not the load.
Two qualifications belong with the feature. The engine's own restart gate is a
3,725/3,726-token run whose warm arm prefilled one token in 0.1 s against 3,774 tokens
cold, and its route table marks disk KV qualified for the V4.1 route
(`docs/deepseek41-flash.md` and `docs/ds41-post-decode-checkpoint.md` on the engine
tree). That gate has not been repeated with this artifact, so treat the saving as the
engine's measurement applied to a compatible base, not as a number measured here.

## The engine floor, and why it is only a warning

The card's speed table is two rounds apart in the engine. Before `2f7a19e5` and
after `58738c04`, PR #147 and PR #149 moved index scores, routed experts with E4M3
activations and the q4_K projections with F16 weights onto tensor cores, and kept
the Engram prefetch buffer:

| 2K-64K sweep, median of the runs' means | Before | After |
|---|---:|---:|
| Prefill tok/s | 955.5 | 1,662.2 |
| Decode tok/s | 32.4 | 32.5 |

Per frontier, after the rounds: 1,291 tok/s at 2K, 1,622 at 8K, 1,717 at 16K,
1,673 at 32K and 1,647 at 64K, with decode between 30.8 and 35.5. VQ and iVQ share
these shapes and kernels. The launcher reports the engine's commit against
`58738c04` in `preflight`, `plan` and `build`, and does not refuse: any build with
the V4.1 route serves the file, it just serves it at the old number. The card's own
kill switches, `DS4_DS41_VQ_FP8=0` and `DS4_DS41_Q4P=0`, restore the earlier
kernels and are not set by the launcher.

## What the author measured on a GB10, with this artifact

Teacher-forced over the same 26 cases as the iVQ card, 44,157 generated positions
and 58,777 in total, the released GGUF through `ds4-server` at `502019da`, against
the original FP4/FP8 checkpoint's reference logits:

| Generated positions | Floor | VQ | iVQ | hVQ |
|---|---:|---:|---:|---:|
| KL | 0.012 | 0.302 | 0.296 | **0.247** |
| Same top-1 as the original | 96.3% | 81.96% | 81.87% | **84.02%** |
| Top-1 is the text's token (original 71.72%) | — | 68.95% | 68.80% | 69.47% |
| NLL (original 1.235) | — | 1.340 | 1.348 | 1.360 |
| Entropy (original 0.816) | — | 1.155 | 1.077 | 0.889 |

All positions, KL: 0.379 VQ, 0.362 iVQ, 0.277 hVQ. The "floor" is the original run
twice under a different batching, so it measures numerical variation, not a
confidence interval.

The NLL column is the one to read carefully. hVQ is closer to the original's
distribution by every KL measure and by top-1, and its NLL is 0.012 worse than
iVQ's — inside the reported interval. The card's explanation is that hVQ is nearly
as sharp as the original and follows it even where the original's top-1 is not the
text's token, while the flatter iVQ hedges; where the original is right, hedging
scores better on that token. So the release buys fidelity to the checkpoint, not
necessarily better text.

The H200 reference forward, which substitutes only the experts, agrees: routed
output error per token 0.309 VQ, 0.288 iVQ, 0.189 hVQ over the 40 layers, final
hidden-state cosine 0.778, 0.798, 0.869, and generated-position KL 0.293, 0.290,
0.241.

Serving was checked too: `ds4 --serving-check` reproduces 16 of 16 tokens on
prefix reuse, continue and disk KV; chat, thinking, SSE, a tool call and its
follow-up, a base64 image, `/v1/messages`, `/v1/responses`, `/v1/completions` and a
24K prompt with one planted fact all answered; and the model was resident 153 s
after launch with 10.5 GiB left. A seeded set of 44 requests per artifact at
temperature 1.0 had hVQ 24/24 on thinking arithmetic, 24/24 closing with `stop`,
12/12 valid tool calls and 8/8 stopped chat, code and translation requests. That
shows no gross failure; it is not a ranking.

## Limits

- About 1.6 bits per routed-expert weight. The card's own summary: fidelity against
  VQ and iVQ improved, NLL slightly worse, no task benchmark, sampled generation
  checked only on the seeded set.
- One 26-case held-out set chose `t`, damping and shrink and then measured the
  build. The card says so; it is not an independent second test.
- The MTP draft towers are VQ's, unchanged. Decode moved by less than its noise
  across the prefill work for that reason, and drafter acceptance on these experts
  is whatever those towers give.
- Thinking is off by default for this weight recipe because it under-weights stop
  decisions; long thinking segments can fail to close. The card's seeded thinking
  requests were short.
- One ds4 model at a time: the engine takes a single global lock.
- The custom VQ format needs ds4-dfm-rs or YoungAi's engine. llama.cpp, Ollama and
  Transformers cannot read it.
- No domain sidecar ships, and YoungAi's V4.1 zchain and GR-RB sidecars do not fit
  these weights, so `--zchain` is never passed.
- Nothing in this repository has been measured on this artifact. Treat the first
  start on the box as the measurement.

## Troubleshooting

- `download` reports a missing `--include` option: the Hugging Face CLI is too old
  to route the parts, the sidecar and the tables to different volumes. Upgrade
  `huggingface_hub`.
- `assemble` stops with "is not in SHA256SUMS": the directory holds parts from
  another 1017 packaging. Delete the parts and fetch this release's.
- `assemble` stops with "hashes to …, not the published …": the parts are this
  release's and the file still is not, which means an interrupted earlier run or a
  manifest from elsewhere. Delete the base and the parts, then fetch again.
- `verify` names the V4.1 tables: point `--engram-dir` at a fresh directory and let
  `download` fetch this release's copies. The tables are 203 GB, so check the
  volume first.
- `start` refuses with "no verification record matches the bytes on disk": run
  `verify`. That refusal is what stops a swapped-in table set from being served.
- `preflight` warns that the engine is older than `58738c04`: it will serve, at
  roughly 955 tok/s prefill instead of 1,662. `git -C ~/ds4-dfm-rs pull`, then
  `bash scripts/install-ds41-1017-hvq.sh build`.
- The port never answers: check `MemAvailable` first — the base is about 106 GiB
  resident, and another owner will starve it. Then read the log; the card reports
  153 s from launch to resident for 113.6 GB.
- A refused start because another model is resident: the engine's global lock is
  doing its job. Stop the other launcher, or pass `--allow-shared` only when you
  know what is running.
