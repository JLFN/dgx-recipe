# Recipe: DeepSeek-V4.1-Flash-1017 VQ on the DS4 CUDA engine

**Superseded on 2026-10-18 by
[`youngai-deepseek-v41-flash-1017`](youngai-deepseek-v41-flash-1017.md).** The
corrected YoungAi packaging names the base and the vision file with 1017, ships
five 1017-specific domain sidecars, and has a different base digest at the same
byte size. This runbook remains for the files already fetched under this
packaging's paths; new deployments should use the new recipe.

DeepSeek's October 17 V4.1 Flash checkpoint, converted the day it shipped with
YoungAi's `vq8sh14-q4k-mtpnative` recipe and packaged so one 128 GB DGX Spark can
hold it. A 510 GB official checkpoint becomes a 113.56 GB base GGUF that carries
the model's own three-tower DSpark drafter, plus a 971 MB vision sidecar and the
1017 Engram tables read from disk.

- Contract: [`recipes/ds41-1017-vq.yaml`](../recipes/ds41-1017-vq.yaml)
- Launcher: [`scripts/start-ds41-1017.sh`](../scripts/start-ds41-1017.sh)
- Artifact: [`Baekpica/DeepSeek-V4.1-Flash-1017-VQ-GGUF`](https://huggingface.co/Baekpica/DeepSeek-V4.1-Flash-1017-VQ-GGUF) at `f81ee2e9`
- Upstream model: `deepseek-ai/DeepSeek-V4.1-Flash-1017` at `1bae0e10`

## What this recipe buys you

A frontier V4.1-class coding and agentic model resident on one Spark at the
native 1,048,576-token context, with speculative decoding built in rather than
bolted on, vision through a sidecar, and retrieval through the model's own
Engram n-gram tables streaming off the SSD. Nothing else in this repository
reaches that depth with that much model behind it.

What it does not buy you is fidelity. The routed experts are 8-dimensional
vector quantization at 1.6 bits per weight. On the V4.1 checkpoint built with
this recipe, the quantized model agreed with the full-precision original's next
token 78.61 percent of the time on code, 78.52 on English, and 69.08 on medicine,
which is a large, deliberate quality drop in exchange for fitting on one box. It
is not a drop-in equal of the FP8 model and the card says so plainly.

The date matters in two places you cannot see by looking at the files. 1017
changed all 48 weight shards, including the two holding the Engram tables, and
the vision tower; the file names and sizes did not change. An engine pointed at
V4.1's tables or an older sidecar loads them without a word and runs a
mismatched model. That is why this launcher hashes both Engram files and the
sidecar against the published digests instead of trusting names, and why the
card publishes those digests as a pair.

## Where the pieces go, and why it is split

`BASE_DIR` (default `/mnt/models/ds41-1017`) holds the base, the vision sidecar
and the manifests. `ENGRAM_DIR` (default `~/models/ds41-1017-engram`) holds the
two tables. They are separate settings because the two halves read in opposite
ways. The base is read once at load and then stays resident at about 106 GiB, so
it belongs on the roomy volume and does not care how slow that volume is. The
Engram tables are read in rows on the tokens that hit an n-gram, which is why the
artifact card asks for a local SSD, so they belong on the fastest device. On the
reference Spark that is the 953 GB volume for the base and NVMe for the tables.

Peak space is not the sum of everything. The download is 318 GB, and the
assembly appends one part at a time and deletes it as it lands, so it needs one
extra part (2.8 GB) rather than another 114 GB. The card's own quick start uses
the same loop.

## Quick start

```sh
bash scripts/start-ds41-1017.sh preflight     # GPU, CUDA 13, memory, both disks, ports
bash scripts/start-ds41-1017.sh download      # 318 GB, resumable
bash scripts/start-ds41-1017.sh assemble      # 40 parts -> the base, verifying each
bash scripts/start-ds41-1017.sh verify        # SHA256SUMS plus the two Engram digests
bash scripts/start-ds41-1017.sh build         # check the flags the engine must advertise
bash scripts/start-ds41-1017.sh start         # serve on 0.0.0.0:8008
```

`plan`, `status`, `logs`, `test` and `all` round it out. Every path, port,
context and memory knob is an environment override documented in the script
header, including `BASE_DIR`, `ENGRAM_DIR`, `MTP_MODE`, `NO_VISION`, `BUDGET_MB`
and `ALLOW_SHARED`.

## The serving command, and the one flag that has no path

The card's line, adapted to this box's port map:

```sh
~/ds4-dfm-rs/ds4-server --cuda -m "$BASE_DIR/DeepSeek-V4.1-Flash-vq8sh14-q4k-mtpnative.gguf" \
    --engram-dir "$ENGRAM_DIR" \
    --vision-gguf "$BASE_DIR/DeepSeek-V4.1-Flash.vision.gguf" \
    --mtp-mode auto --mem-budget-mb 110000 --host 0.0.0.0 --port 8008
```

The drafter is embedded in the base, so `--mtp-mode` only selects behaviour
(`off`, `auto`, `on`) and there is no `--mtp` path to give. The engine reads only
the two shard file names out of the GGUF, so `--engram-dir` can point at your own
copy of the 1017 checkpoint instead of the one fetched here.

## Thinking, sampling, and the caveat the recipe carries

DeepSeek recommends `temperature` 1.0 and `top_p` 1.0 for 1017 and the card says
to send both explicitly, because sampling on this path follows the request rather
than a server-side recipe. The launcher's smoke test sends them.

YoungAi reports that this weight recipe under-weights stop decisions
(`response`, EOS), so a long thinking segment can fail to close. Its own server
therefore defaults to non-thinking mode, and ds4-dfm-rs does the same for this
family: thinking is opt-in per request. If you go looking for a runaway thinking
loop on this artifact, that is the documented mechanism, not a control-plane bug.

## The memory budget

The card's engine budget is `--mem-budget-mb 110000`, against a 121.6 GiB box,
with the base resident at about 106 GiB. YoungAi measures the full 1M-token KV
cache of this architecture at 0.89 GB, so context depth is not what constrains
the Spark here; the base weights are.

That leaves a thin margin, which is why the launcher runs a watchdog: two
consecutive `MemAvailable` samples below 2500 MB stop the server, and the
preflight floors are 100,000 MB before loading and 8,000 MB after. Nothing in
this section was measured on 1017 by this repository. It is the card's figure for
the same recipe on V4.1 Flash, and it is labelled that way in the recipe
contract. `--check-config` would settle it; the launcher's `plan` action prints
what a start would run with, without opening the weights.

## What is measured, and what is not

Measured by this repository: nothing yet. The launcher has been exercised against
fixtures for its argument assembly, its guards and its plan output, and its
download and assemble steps are the card's own procedure with resumption and
per-part verification added. No 1017 download, load or request has been run here.

Measured by others, for this recipe on **V4.1 Flash** (not 1017): decode 38.17
tok/s median over a 2K to 64K sweep on one Spark, 42.6 tok/s at the 2K frontier,
and 54.10 tok/s on short code prompts on a later engine build; prefill 1039.65
tok/s median, 1222.4 at 16K on that later build. Speeds should be close on 1017
because decode is bound by memory bandwidth and the two read the same bytes per
token, but drafter acceptance follows the generated text, so treat that as a
prediction.

Not measured anywhere yet: 1017's own speed, its fidelity to the FP8 original,
and its long-context behaviour.

## Checks

- `verify` hashes the assembled base, the vision sidecar, and — the ones worth
  waiting for — the two 101.5 GB Engram tables, because those are the files a
  V4.1 copy would silently replace.
- `build` refuses a `ds4-server` that does not advertise `--engram-dir`,
  `--vision-gguf`, `--mem-budget-mb` and `--mtp-mode`, which is how a stale
  binary fails here.
- `plan` prints the exact serving command and the bytes still to fetch, without
  touching the weights.

## Troubleshooting

- `the server exited while loading`: check the tail the launcher prints. A short
  load usually means the engram directory is wrong or a shard is short.
- Images come back as text-only answers: the sidecar was not mounted. Drop
  `NO_VISION=1` and re-run `start`.
- Answers look subtly wrong with no error anywhere: suspect a V4.1 Engram table
  or an older vision sidecar under the 1017 names. Run `verify`.
- `only N MB of memory available`: another ds4 model is resident. One runs at a
  time here.
- The endpoint binds late: the card reports about two minutes to load 113 GB.
